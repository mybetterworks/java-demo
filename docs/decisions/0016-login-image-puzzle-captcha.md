# 0016 Login Image Puzzle Captcha

## 状态

已采纳。

## 日期

2026-06-03，Asia/Shanghai。

## 背景

`v0.5.4 Login Slider Captcha` 已经完成登录风险验证闭环：同一登录主体 5 分钟内失败 3 次后，需要完成滑块验证码才能继续登录。该版本的价值是跑通失败计数、challenge、verify、一次性 `captchaToken` 和 React/Vue 前端联动。

但是 `v0.5.4` 的滑块验证码仍是学习型 MVP。当前滑块答案可以由前端参数推导，脚本可以自动请求 challenge、计算位置、调用 verify 并获得 `captchaToken`。因此它能阻止“不走验证码流程”的直接请求，但不能有效抵御模拟前端流程的自动化脚本。

为了让登录验证更接近真实业务，需要在进入 Nacos、Redis 等基础设施阶段前，先补齐验证码本身的安全性。

## 决策

在 `v0.5.5` 新增固定背景图随机拼图滑块验证码。

| 项目 | 决策 |
|---|---|
| 背景图 | 使用项目内置固定背景图，随后端应用打包 |
| 缺口位置 | 每次 challenge 由后端随机生成缺口位置 |
| 答案保存 | 正确 `targetX` 只保存在服务端，不返回前端 |
| 前端展示 | 前端只展示背景缺口图、拼图块图、轨道和提示 |
| 校验方式 | 后端校验滑动坐标、耗时、基础轨迹和一次性状态 |
| 状态存储 | 本版本仍可使用单机内存，`v0.7 Redis` 再迁移分布式 TTL |
| 前端范围 | React 和 Vue 登录页都要同步升级 |
| 安全边界 | 不打印密码、完整 JWT、验证码答案、Base64 图片全文或验证码 token |

## 设计原则

1. 答案不能从接口响应字段直接推导。
2. 缺口位置必须随机，不能固定为终点或固定偏移量。
3. challenge 必须短 TTL、一次性或有限失败次数。
4. 验证通过 token 必须短 TTL、一次性消费，并绑定同一 `username + clientIp`。
5. 前端体验要清晰，但不能把安全判断交给前端。
6. 当前版本不引入重型风控系统，避免一次性复杂化。

## 与 v0.5.4 的关系

`v0.5.5` 不推翻 `v0.5.4` 的登录风险流程，而是替换验证码挑战本身。

| 能力 | `v0.5.4` | `v0.5.5` |
|---|---|---|
| 失败计数 | 保留 | 继续保留 |
| 风险触发 | 5 分钟失败 3 次 | 继续保留 |
| challenge/verify 接口 | 已有 | 路径尽量复用 |
| 验证码形式 | 轻量滑块 | 固定背景图随机拼图滑块 |
| 答案暴露风险 | 前端可推导 | 服务端保存，前端不可获得 |
| 前端联动 | React/Vue 已支持 | React/Vue 升级交互 |

## 安全边界

本决策目标是抵御普通脚本自动化，不承诺抵御所有真实世界攻击。

能够提升的点：

1. 脚本不能再只通过接口返回字段计算答案。
2. 每次缺口位置随机，不能直接复用固定滑动距离。
3. 错误位置、过短耗时和明显异常轨迹会被拒绝。
4. challenge 和 token 都是短 TTL、一次性状态。

仍然存在的边界：

1. 专业图像识别仍可能识别缺口。
2. 打码平台或人工介入仍可能绕过验证码。
3. 单机内存状态不适合多实例部署。
4. 没有 Redis 前，challenge 请求频率限制只能做单机级别。

因此 `v0.7 Redis` 仍需要继续迁移验证码状态和限流状态；更高等级的真实生产防护还需要设备指纹、行为模型、WAF、黑名单或第三方验证码服务。

## 影响

1. `v0.5.5` 成为 `v0.6 Nacos` 之前的安全增强版本。
2. `v0.5.5` 已完成后，README、PROGRESS 和 milestone 文档需指向下一步 `v0.6 Nacos`。
3. 后续回归验证登录时，需要覆盖固定背景图随机拼图验证码，避免服务治理、缓存或网关改造破坏登录安全链路。
4. 日志和注释规则继续继承 `v0.5.2`，并额外禁止打印图片全文、验证码真实坐标和一次性验证码 token。
