# v0.6.1 OpenFeign Service Calls

## 版本结论

`v0.6.1 OpenFeign Service Calls` 已于 `2026-06-04` 完成。

本版本在 `v0.6 Nacos` 已完成服务注册发现和配置中心的基础上，把 `task-service -> java-demo-app` 的用户校验链路，以及 `task-service -> notification-service` 的通知创建链路，从手写 REST 调用改为基于 Nacos 服务名的 OpenFeign 声明式 HTTP 调用。

本版本没有新增前端页面，也没有改变 Gateway 对外接口路径；React 和 Vue 的主要职责是做构建回归，确认内部服务调用方式切换后，现有用户可见能力没有被破坏。

## 目标

1. 在不回退 `v0.6` Nacos 服务发现的前提下，引入 OpenFeign。
2. 只改造 `task-service` 的两条同步 HTTP 下游链路，不引入 Dubbo，不提前改 MQ。
3. 保持 JWT 语义、`X-Request-Id` 透传、关键日志和统一异常语义。
4. 完成自动化测试、前端构建回归和真实 Gateway 联调。

## 实际新增能力

声明式服务间 HTTP 调用。

```text
task-service
  -> OpenFeign -> java-demo-app
  -> OpenFeign -> notification-service
```

本版本完成后：

1. `task-service` 不再自己拼接用户服务和通知服务 URL。
2. Feign Client 直接使用 Nacos 服务名进行发现。
3. `task-service` 健康检查会返回 `serviceCallMode=openfeign`，便于联调时确认当前主路径。
4. 任务创建链路中的 `Authorization` 和 `X-Request-Id` 会显式透传到下游服务。

## 改造范围

| 调用方 | 被调用方 | 业务目的 | `v0.6.1` 实现 |
|---|---|---|---|
| `task-service` | `java-demo-app` | 创建或更新任务时校验负责人用户是否存在 | 已改为 OpenFeign |
| `task-service` | `notification-service` | 任务创建、分配或状态变化后创建站内通知 | 已改为 OpenFeign |

不在本版本改造：

| 不改造项 | 说明 |
|---|---|
| 前端到 Gateway | 外部入口继续保持 REST/HTTP |
| Gateway 到后端服务 | Gateway 继续使用 HTTP 路由和 Nacos 服务发现 |
| `java-demo-app -> notification-service` | 当前不是主线必需链路，暂不扩展 |
| Dubbo RPC | 留到 `v0.6.2` 单独学习 |
| MQ 异步通知 | 留到 `v1.0`，避免和 Feign 改造叠加复杂度 |

## 关键实现说明

### 1. 业务层没有直接注入 Feign，而是保留包装层

本版本没有让 `TaskService` 直接依赖 `UserFeignClient` 或 `NotificationFeignClient`。

实际实现中继续保留：

1. `UserServiceClient`
2. `NotificationServiceClient`

这样做的原因是把以下横切逻辑集中在一个边界里：

1. `Authorization` 头拼装与透传。
2. `X-Request-Id` 读取与透传。
3. 下游 `4xx` / `5xx` / 超时的统一异常映射。
4. 关键日志打印与敏感信息保护。

这样 `TaskService` 仍然只关心“需要校验用户”和“需要创建通知”两个业务动作，不关心 Feign 细节。

### 2. Feign Client 直接使用 Nacos 服务名

本版本不再使用：

1. `JAVA_DEMO_USER_SERVICE_URL`
2. `JAVA_DEMO_NOTIFICATION_SERVICE_URL`

改为使用：

1. `JAVA_DEMO_USER_SERVICE_NAME`
2. `JAVA_DEMO_NOTIFICATION_SERVICE_NAME`

对应默认值分别是：

1. `java-demo-app`
2. `notification-service`

这样 Feign 会直接走 `Spring Cloud LoadBalancer + Nacos` 的服务发现主路径。

### 3. `Authorization` 和 `X-Request-Id` 显式透传

本版本没有把 JWT 解析逻辑复制到下游，而是在包装层里显式把当前用户 token 重新拼成 Bearer 头，继续交给 `java-demo-app` 和 `notification-service` 沿用原有鉴权语义。

同时会从 MDC 中读取当前 `requestId`，作为 `X-Request-Id` 传给下游服务，便于在三个服务的日志中串联同一次任务链路。

### 4. 异常映射按业务语义区分

用户服务链路：

1. 下游返回 `404` 时，转换为 `BusinessException.badRequest("Assignee user does not exist")`。
2. 下游返回 `401` 时，转换为 `BusinessException.unauthorized("User service rejected current token")`。
3. 连接失败、超时和其他异常统一转换为 `502` 下游错误。

通知服务链路：

1. 连接失败、超时、`4xx`、`5xx` 统一转换为 `502` 下游错误。
2. 当前版本仍把通知创建视为同步强依赖，让失败显式暴露，便于后续和 `v1.0 MQ` 对比。

### 5. 健康检查和启动日志显式暴露 Feign 主路径

`task-service` 的健康检查响应新增：

1. `serviceCallMode=openfeign`
2. `userServiceName`
3. `notificationServiceName`

启动日志新增：

1. Feign 连接超时
2. Feign 读取超时
3. Feign 日志级别
4. Nacos 地址
5. 目标服务名

这样在排查环境问题时，可以快速判断当前进程是否真的进入了 `OpenFeign + Nacos` 主路径。

### 6. 测试策略从 REST Mock 切换为 Feign Mock

`TaskIntegrationTest` 继续保留真实的任务服务 HTTP 入口、JWT 拦截器和 H2 数据库，但把下游依赖替换为：

1. `@MockBean UserFeignClient`
2. `@MockBean NotificationFeignClient`

这样既能验证任务服务自己的接口行为，又能精确断言：

1. Bearer token 是否被透传。
2. `X-Request-Id` 是否被透传。
3. 用户不存在时是否仍返回原有业务错误。
4. 通知服务失败时是否仍回滚任务并返回 `502`。

### 7. 实际踩坑记录

实现过程中确认了一个容易踩的点：

1. Feign 接口不要继续保留类级 `@RequestMapping` 作为主路径。
2. 最终实现改为把公共路径写在 `@FeignClient(..., path = "...")` 上，再在方法级使用 `@GetMapping` / `@PostMapping`。

这样可以避免 Feign 接口初始化阶段的映射冲突和不兼容问题。

## 与原计划的差异

| 项目 | 原计划 | 实际实现 |
|---|---|---|
| 业务调用入口 | 可以直接由业务层使用 Feign | 保留包装层，再由包装层内部调用 Feign |
| 前端改动 | 需要评估是否同步调整 | 实际无需改动前端代码，因为用户可见接口与字段未变化 |
| 通知失败策略 | 需要明确错误处理 | 继续按同步强依赖处理，通知失败时返回 `502` 并回滚 |

这些差异都没有偏离 milestone 目标，反而让边界更清晰，便于后续 `v0.6.2` 只替换用户校验链路时继续复用现有包装层结构。
