## 目标

在保留 `v0.5.4` 登录失败风险判断规则的基础上，增强验证码本身的安全性：

```text
同一登录主体 5 分钟内登录失败 3 次
  -> 后端生成固定背景图上的随机拼图缺口
  -> 前端展示背景缺口图和拼图块
  -> 用户拖动拼图块到缺口位置
  -> 后端校验滑动位置、耗时和基础轨迹
  -> 校验通过后签发一次性 captchaToken
  -> 用户携带账号密码 + captchaToken 登录
```

本版本重点不是引入第三方验证码平台，而是在当前项目技术栈内实现一个更接近真实业务的验证码闭环：**答案不下发、缺口随机、挑战一次性、结果短 TTL、日志不泄露敏感信息、React/Vue 双端联动一致**。

## 为什么需要本版本

`v0.5.4` 已经跑通了登录风控流程，但当前滑块答案可以由前端参数推导，例如 `trackWidth - puzzleWidth`。脚本可以自动调用 challenge、verify 和 login 三个接口完成验证，因此它更适合学习流程，不适合作为真实自动化攻击防护。

`v0.5.5` 要解决这个问题：

| 问题 | `v0.5.4` 现状 | `v0.5.5` 要求 |
|---|---|---|
| 验证码答案 | 前端可推导终点位置 | 后端随机生成缺口位置，前端不可获得真实答案 |
| 图片挑战 | 无真实拼图图片 | 使用固定背景图生成带缺口背景和拼图块 |
| 自动化脚本 | 可按公式自动通过 | 脚本无法只靠接口字段直接算出答案 |
| 用户交互 | 简单滑动到终点 | 拖动拼图块到图片缺口位置 |
| 校验维度 | 只校验滑动位置 | 校验位置、耗时、基础轨迹和一次性状态 |

说明：本版本能显著提升对普通脚本自动化的抵御能力，但仍不承诺抵御专业打码平台、浏览器自动化识图或人工验证码服务。真实生产系统还应结合限流、设备指纹、行为分析、黑名单、WAF 或第三方验证码平台。

## 新增能力

登录拼图滑块验证码增强。

```text
java-demo-app
  -> 固定背景图资源
  -> 随机缺口位置
  -> 生成带缺口背景图
  -> 生成拼图块图
  -> 保存 challengeId -> 正确 x 坐标、y 坐标、过期时间、风险 key
  -> 校验前端拖动结果
  -> 返回一次性 captchaToken

React / Vue 登录页
  -> 展示背景缺口图和拼图块
  -> 用户拖动拼图块
  -> 提交 challengeId、滑动坐标、耗时和基础轨迹
  -> 验证通过后继续登录
```

## 功能范围

| 功能 | 说明 |
|---|---|
| 固定背景图 | 使用项目内置固定图片作为验证码背景，避免额外引入上传或对象存储 |
| 随机缺口位置 | 每次 challenge 在安全范围内随机生成缺口 `x` 坐标，`y` 坐标也可以在小范围内随机或按固定行生成 |
| 背景缺口图 | 后端基于固定背景生成“带缺口”的背景图，前端只负责展示 |
| 拼图块图 | 后端从原图裁剪出拼图块，前端展示并随拖动移动 |
| 服务端答案 | 后端只保存正确缺口坐标，不把真实 `targetX` 返回给前端 |
| 基础轨迹 | 前端提交拖动耗时、轨迹点数量、起止位置等轻量信息，后端做基础合理性校验 |
| 一次性 challenge | challenge 校验成功、失败次数过多或过期后失效 |
| 一次性 token | 验证通过后返回短 TTL `captchaToken`，登录接口消费后立即失效 |
| 登录流程复用 | 继续复用 `v0.5.4` 的失败计数、`4601/4602` 业务码和登录重试流程 |
| 双前端联动 | React 和 Vue 登录页都必须支持拼图滑块展示、拖动、校验、刷新和错误提示 |

## 非目标

1. 不引入第三方验证码平台。
2. 不在本版本强制引入 Redis；状态仍可先使用单机内存，`v0.7 Redis` 再迁移。
3. 不做复杂设备指纹、浏览器指纹、WAF 或黑名单系统。
4. 不承诺抵御专业图像识别、打码平台或人工绕过。
5. 不改变登录成功后的 JWT 签发和登录态保存方式。

## 后端实现要求

### 图片生成

| 要求 | 说明 |
|---|---|
| 固定背景 | 背景图作为 classpath 资源加载，例如 `captcha/backgrounds/login-bg-01.png` |
| 图片尺寸 | 后端统一裁剪或缩放到固定宽高，前端按返回尺寸渲染 |
| 随机缺口 | `targetX` 必须由后端随机生成，避开最左、最右和过低可用区域 |
| 拼图形状 | MVP 可使用圆角矩形、凹凸拼图形状或带阴影遮罩；优先保证清晰可见 |
| 背景缺口 | 后端在背景图上绘制半透明缺口、阴影或高亮边缘 |
| 拼图块 | 后端从原图对应位置裁剪拼图块，并保持与缺口形状一致 |
| 返回格式 | 可以返回 Base64 图片数据，也可以返回当前 challenge 的临时图片访问路径；MVP 推荐 Base64，减少额外静态资源路由 |

### Challenge 状态

| 状态字段 | 说明 |
|---|---|
| `challengeId` | 随机 ID，前端 verify 时提交 |
| `riskKey` | 绑定 `username + clientIp`，避免跨账号或跨客户端复用 |
| `targetX` | 正确缺口横向位置，只保存在服务端 |
| `targetY` | 缺口纵向位置，可返回给前端用于展示拼图块纵向位置，但不作为完整答案 |
| `expiresAt` | 建议 2 分钟 TTL |
| `failCount` | 单个 challenge 的错误次数，超过限制后失效 |
| `createdAt` | 用于校验验证耗时是否合理 |

### 校验规则

| 校验项 | 建议 |
|---|---|
| 坐标容差 | 允许 `±5px` 左右误差，具体值写成常量 |
| 最短耗时 | 低于极小值，例如 `300ms`，判定为疑似脚本 |
| 轨迹点数量 | 至少有多个轨迹点，避免瞬间跳到终点 |
| 轨迹方向 | 轨迹整体应从左向右移动，允许少量抖动 |
| 一次性 | 成功后 challenge 立即删除；失败次数达到限制也删除 |
| 过期 | challenge 超过 TTL 后返回 `4602`，前端重新获取 |
| token 绑定 | 验证通过 token 继续绑定同一 `username + clientIp` |

注意：轨迹校验只做基础反自动化，不要把本版本做成复杂风控系统。目标是让脚本不能只通过读取接口字段直接算出答案。

## 推荐接口设计

尽量复用 `v0.5.4` 接口路径，避免前端和网关重复改造。

| 方法 | 路径 | 说明 | 是否需要 JWT |
|---|---|---|---|
| `POST` | `/api/auth/login` | 登录；风险状态下需要携带 `captchaToken` | 否 |
| `POST` | `/api/auth/captcha/slider` | 生成拼图滑块 challenge | 否 |
| `POST` | `/api/auth/captcha/slider/verify` | 校验拼图滑块结果并返回一次性 token | 否 |

Challenge 响应建议：

```json
{
  "challengeId": "random-id",
  "backgroundImage": "data:image/png;base64,...",
  "puzzleImage": "data:image/png;base64,...",
  "trackWidth": 320,
  "imageWidth": 320,
  "imageHeight": 160,
  "puzzleWidth": 48,
  "puzzleHeight": 48,
  "puzzleY": 72,
  "expiresInSeconds": 120,
  "instruction": "请拖动拼图块到缺口位置"
}
```

禁止在响应中返回：

1. `targetX`。
2. 正确答案。
3. 服务端校验密钥。
4. 可直接复用的验证码 token。

Verify 请求建议：

```json
{
  "challengeId": "random-id",
  "sliderX": 132,
  "durationMs": 1460,
  "tracks": [
    { "x": 0, "y": 0, "t": 0 },
    { "x": 18, "y": 1, "t": 120 },
    { "x": 132, "y": 0, "t": 1460 }
  ]
}
```

Verify 成功响应继续复用：

```json
{
  "captchaToken": "one-time-token",
  "expiresInSeconds": 120
}
```

业务码继续沿用：

| 业务码 | 语义 |
|---|---|
| `4601` | 当前登录主体需要完成验证码 |
| `4602` | 验证码错误、过期、轨迹异常或 token 无效 |

## 日志要求

继承 `v0.5.2` 后端运行日志基线，并强化验证码敏感信息边界。

| 场景 | 建议级别 | 日志内容 |
|---|---|---|
| 生成拼图 challenge | `INFO` | challengeId、username、clientIp 摘要、图片尺寸、TTL |
| 校验成功 | `INFO` | challengeId、username、clientIp 摘要、耗时、轨迹点数量 |
| 坐标错误 | `WARN` | challengeId、坐标偏差摘要，不打印正确答案 |
| 轨迹异常 | `WARN` | challengeId、异常原因、耗时、轨迹点数量 |
| challenge 过期 | `WARN` | challengeId、过期原因 |
| token 消费成功 | `INFO` | username、clientIp 摘要，不打印 token |

禁止打印：

1. 明文密码。
2. 完整 JWT。
3. Authorization header。
4. `targetX`、完整答案或原始拼图答案。
5. `captchaToken` 原文。
6. Base64 图片全文。

## 数据与状态存储

本版本继续优先保持最小可运行，不强制引入 Redis。

| 状态 | MVP 存储 | 后续演进 |
|---|---|---|
| 登录失败计数 | 复用 `v0.5.4` 单机内存 | `v0.7 Redis` 使用 TTL key |
| 拼图 challenge | 单机内存保存答案、过期时间、风险 key、失败次数 | `v0.7 Redis` 使用 TTL hash 或 JSON |
| 验证通过 token | 单机内存短 TTL，一次性消费 | `v0.7 Redis` 使用短 TTL key |
| challenge 请求频率 | 本版本可用单机内存做轻量限制 | `v0.7 Redis` 接入分布式限流 |

如果实现过程中发现单机内存对象增长风险，必须补充懒清理或定期清理策略。

## 验收标准

1. 5 分钟内登录失败 3 次后仍能触发验证码要求。
2. Challenge 响应包含背景缺口图和拼图块图，但不包含真实 `targetX` 或答案。
3. 每次 challenge 的缺口横向位置随机变化。
4. 前端不能通过 `trackWidth - puzzleWidth` 这类固定公式直接得到答案。
5. 错误滑动位置返回 `4602`，不会签发 `captchaToken`。
6. 耗时过短、轨迹点过少或轨迹明显异常时返回 `4602`。
7. 正确滑动位置、合理耗时和基础轨迹通过后返回一次性 `captchaToken`。
8. `captchaToken` 只能用于同一 `username + clientIp` 的下一次登录。
9. `captchaToken` 被登录接口消费后不能重复使用。
10. 登录成功后清理失败计数、challenge 和 token 状态。
11. React 登录页可完成拼图滑块验证和登录重试。
12. Vue 登录页可完成拼图滑块验证和登录重试。
13. Gateway 继续放行验证码 challenge 和 verify 公开接口。
14. 日志可观察验证码生成、校验成功、校验失败和异常原因，但不泄露答案、token、密码或完整 JWT。
15. 新增和修改代码已补充详细中文注释。
16. 后端测试、真实 Gateway 联调、React 构建和 Vue 构建通过，或明确记录无法验证原因。
