# v0.8 WebSocket

## 状态

已完成，完成时间：2026-06-07，Asia/Shanghai。

本版本在 `v0.7 Redis Cache And Rate Limit` 的基础上引入 WebSocket 实时通知能力。核心入口放在 `notification-service`，路径为 `/ws/notifications`；Gateway 通过 `/ws/notifications/**` 转发到通知服务；React 和 Vue 登录后自动连接实时通知通道，并在通知中心收到业务推送后刷新通知列表和未读数。

## 目标

引入 WebSocket，实现服务端向前端推送基础消息，包括连接确认、系统广播、通知创建、未读数量变化和心跳响应。

本版本刻意不引入 STOMP、MQ 或跨实例推送总线，先完成单实例可运行闭环，便于学习 WebSocket 最小实现、握手鉴权、前端重连和通知业务联动。

## 新增能力

| 能力 | 实现结果 |
|---|---|
| WebSocket endpoint | `notification-service` 新增 `/ws/notifications` |
| 握手鉴权 | 握手阶段解析 JWT，兼容 `Authorization: Bearer ...` 和浏览器使用的 `?token=...` |
| Gateway 转发 | Gateway 新增 `/ws/notifications/**` -> `${JAVA_DEMO_NOTIFICATION_WS_URI:lb:ws://notification-service}` |

| 点对点推送 | 创建通知后向目标用户推送 `NOTIFICATION_CREATED` 和 `UNREAD_COUNT_CHANGED` |
| 广播推送 | `POST /api/notifications/system/broadcast` 推送不入库的 `SYSTEM_BROADCAST` |
| 心跳响应 | 客户端发送 `PING` 时服务端返回 `PONG` |
| 前端接入 | React/Vue 登录后自动连接，断开后延迟重连，登出后主动关闭 |

| 日志观察 | 记录握手成功/失败、连接建立/断开、点对点推送、广播推送和推送失败，禁止打印完整 JWT、Authorization header 或 token 原文 |

| 功能 | 实现说明 |

## 消息格式

统一消息体类为 `NotificationWebSocketMessage`。不同 `type` 只填充自己需要的字段，前端按 `type` 判断是否刷新通知中心、更新未读数或展示提示。

```json
{
  "eventId": "uuid",
  "type": "NOTIFICATION_CREATED",
  "receiverUserId": 1,
  "title": "实时任务提醒",
  "content": "你有一个新的任务通知",
  "notification": {},
  "unreadCount": 1,
  "onlineSessionCount": 1,
  "createdAt": "2026-06-07T08:00:00+08:00"
}
```

| 消息类型 | 触发时机 | 前端处理 |
|---|---|---|
| `CONNECTION_ACK` | WebSocket 连接建立后 | 更新连接状态，不刷新通知列表 |
| `NOTIFICATION_CREATED` | 通知创建事务提交后 | 展示提示，刷新通知列表和未读数 |
| `UNREAD_COUNT_CHANGED` | 通知创建、单条已读或全部已读事务提交后 | 更新未读数，刷新通知列表 |
| `SYSTEM_BROADCAST` | 调用系统广播接口后 | 展示系统消息提示 |
| `PONG` | 客户端发送 `PING` 后 | 心跳响应，不刷新通知列表 |

## 事务边界

通知推送使用 after-commit 触发。原因是通知创建、单条已读和全部已读都依赖数据库事务，如果在事务提交前就推送，后续一旦回滚，前端会看到数据库中不存在或状态不一致的“幽灵通知”。

当前处理方式：

1. `NotificationService#createNotification` 先写入数据库并清理未读数缓存。
2. 注册 after-commit 回调。
3. 事务提交后重新计算未读数并写回缓存。
4. 推送 `NOTIFICATION_CREATED` 和 `UNREAD_COUNT_CHANGED`。
5. `markRead` 和 `markAllRead` 同样在提交后推送新的未读数。

## 前端联动

React 端新增 `frontend-react/src/api/realtime.ts` 构造 WebSocket 地址，在 `App.tsx` 管理连接状态、重连定时器和最近消息；`AppShell` 展示顶部“实时通知”状态；`NotificationCenter` 根据推送消息刷新未读数和通知列表。

Vue 端新增 `frontend-vue/src/api/realtime.js` 和 `frontend-vue/src/composables/useNotificationSocket.js`，用组合式函数管理连接、断线重连和消息状态；`AppLayout` 展示实时通知状态；`NotificationCenterView` 和 `useNotificationCenter` 根据推送消息刷新列表与未读数。

两套前端都遵循同一用户体验：

1. 未登录时不连接。
2. 登录后立即连接 `/ws/notifications`。
3. 连接中、已连接、重连中、关闭和错误状态在顶部可见。
4. 收到 `CONNECTION_ACK` 和 `PONG` 只更新连接语义，不打扰用户。
5. 收到业务推送时给出提示，并刷新通知中心。

## 已知边界

| 边界 | 说明 | 后续方向 |
|---|---|---|
| 单实例 session registry | 当前在线连接只保存在单个 `notification-service` JVM 内存中 | 多实例部署时引入 Redis Pub/Sub、MQ、专门 WebSocket 网关或 sticky session |
| token 查询参数 | 浏览器 WebSocket 不能自定义 `Authorization` header，因此前端用 `?token=...` | 后续可在 HTTPS 下配合短期 WebSocket ticket，减少 JWT 暴露面 |
| Gateway 真实转发联调 | 本轮受 Docker Desktop API 不可访问限制未完成 | Docker 恢复后补做 `/ws/notifications` 经 Gateway 的真实连接、广播和任务通知推送验证 |
| 不引入 STOMP | 当前用简单 JSON 消息协议 | 后续如果需要订阅、主题、确认机制和复杂路由，再评估 STOMP 或 MQ |
